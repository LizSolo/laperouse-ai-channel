# Агент(ы) для Telegram-канала LaperouseAI

## Задача (из обсуждения)

Настроить агента/агентов, которые:
- собирают новости из первоисточников (Anthropic и, возможно, другие AI-лабы)
- пишут краткий пересказ + личную оценку/комментарий к материалу
- постят это в Telegram-канал/группу

## Черновой набросок архитектуры

1. **Источники** — RSS/Atom-ленты блогов (у Anthropic, OpenAI и т.д. часто есть фиды), для остальных — периодический просмотр страницы через web-fetch.
2. **Планировщик** — задача по расписанию (cron-агент / routine), проверяет источники на новое, например раз в несколько часов.
3. **Дедупликация** — простое хранилище (файл или маленькая база) со списком уже опубликованного, чтобы не постить повторно.
4. **Обработка** — агент читает новый материал, пишет краткий пересказ и свою оценку в нужном тоне.
5. **Публикация** — пост в Telegram через Bot API (нужен токен бота и права на постинг в канал/группу).

## Ответы, полученные 2026-07-28

- **Бот и группа уже есть.** Тестовые посты сначала кидаем в группу, смотрим как выглядит, потом решаем по каналу. Название бота/токен — пришлёт отдельно.
- **Источники — шире, не только AI-лабы.** Нужны в целом последние новости про AI-технологии (не только Anthropic/OpenAI и т.п.), т.е. нужен более широкий список источников (тех-медиа, где выходят свежие AI-новости), не только один сайт (упоминался TechCrunch как пример, но одного источника мало).
- **Угол подачи / личная оценка:** каждую новость оценивать с точки зрения пользы для малого и среднего бизнеса, в любых нишах — кроме самих AI-компаний. Примеры того, что малый бизнес мог бы закрыть с помощью AI: свой сайт/приложение, бухгалтерия, юристы/договорной отдел (контракты), продажники, служба поддержки — в общем, обычные функции, которыми пользуется малый бизнес.
- **Тон текста:** не должно быть заметно, что текст написан ИИ — живой, человеческий стиль изложения.
- **Частота/расписание:** сводка каждый день в 9:00 по Таиланду.
- **Рабочий процесс:** сводка готовится → пользователь смотрит и решает, что постить и нужна ли правка, перед публикацией (человек в контуре, не полностью автономная публикация).

## Схема из двух агентов (2026-07-31, вечер)

Обсуждали, не сделать ли четыре роли (сборщик → фактчекер → писатель → редактор). Пришли к двум агентам и вот почему.

**Проверка фактов должна идти ПОСЛЕ написания, а не до.** Единственный реальный провал (выдуманный «API Monster» для 1С) возник не из плохого источника: новость и факты в ней были настоящие. Модель выдумала деталь в момент написания, добавляя «полезную конкретику» в абзац. Проверяющий, работающий до написания, такое не поймает в принципе.

**Сборщик и автор не разделяются.** Тот, кто выбрал новость, понимает, чем она цепляет. Разделение теряет эту связь и добавляет лишнюю передачу между сессиями.

**Автор и редактор — обязательно разные сессии.** В одной сессии модель защищает то, что сама написала: она помнит свои доводы. Свежая сессия видит только текст и источник, ей нечего оправдывать. Это и есть настоящая независимость, ради которой стоит разделение.

**Редактор совмещает фактчек и стиль** — он читает тот же готовый текст, отдельный третий агент был бы лишним звеном.

**Чего схема не чинит:** выбор темы и ощущение голоса. Две копии одной модели имеют схожие представления о том, что интересно, поэтому редактор здесь будет соглашаться чаще, чем надо. Это остаётся на человеке — и лечится не агентами, а файлом `FEEDBACK.md`.

## РЕШЕНО: независимая публикация работает (2026-07-31, вечер)

Раньше считали блокировку непреодолимой. Ошибка была в диагностике: две ошибки 403 выглядели одинаково, но были разной природы.
- **Telegram:** «proxy вернул 403 на CONNECT» — сетевая политика окружения, хост недостижим. Это правда непреодолимо изнутри routine.
- **git push:** обычный «403 Forbidden» от GitHub, при том что `git clone` в том же окружении работал. То есть сеть до github.com есть, не хватало только прав (токена). Вывод «архитектурно read-only» был поспешным.

**Рабочая схема (без ноутбука, без новых расходов):**
1. Routine в 9:00 ищет новости, пишет посты, полностью перезаписывает `DRAFTS.md` и делает `git push` с fine-grained PAT (токен зашит в промпт routine).
2. Push запускает GitHub Action `.github/workflows/publish-drafts.yml`, которая вызывает `.github/scripts/send_drafts.py`.
3. Скрипт достаёт из `DRAFTS.md` все блоки в тройных обратных кавычках и отправляет содержимое каждого отдельным сообщением в тестовую группу (parse_mode=HTML, превью отключено).
4. Пользователь читает готовые посты прямо в Telegram на телефоне.

Проверено сквозным прогоном 2026-07-31: routine запушила → Action отработала за 15 сек → два поста ушли в группу (message_id 49, 50).

**Почему бесплатно:** GitHub Actions для публичных репозиториев без лимитов; «думает и пишет» по-прежнему routine из подписки. Anthropic API не задействован.

**Ключевые технические детали:**
- Токен бота и chat_id лежат в GitHub Secrets репозитория (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`), не в коде.
- Fine-grained PAT: доступ только к репозиторию `laperouse-ai-channel`, права Contents + Workflows = Read and write. **Срок действия 90 дней — истекает примерно 2026-10-29, потребуется перевыпуск и замена в промпте routine.**
- Формат `DRAFTS.md` несущий: скрипт шлёт содержимое КАЖДОГО блока с тройными кавычками. Посторонние блоки в файле приведут к лишним сообщениям. Routine обязана перезаписывать файл целиком, иначе старые посты уйдут повторно.
- OAuth-токен gh CLI не может пушить workflow-файлы (нет scope `workflow`) — для изменений в `.github/workflows/` использовать PAT.

**Что изменилось в рабочем процессе:** группа теперь не «превью, которое публикует ассистент вручную», а место, куда посты приходят автоматически. Человеческая вычитка фактов из цикла ушла — вместо неё в промпте усилено требование подтверждать каждый факт двумя независимыми источниками. Канал (когда появится) остаётся ручным: туда публикуется только то, что пользователь одобрила.

## WebFetch полностью заблокирован в облачном окружении (2026-08-01)

При плановом прогоне автора обнаружено: `WebFetch` и прямой `curl` из этой сессии получают 403 на CONNECT абсолютно для всех хостов без исключения, включая нейтральные (example.com, google.com) и даже anthropic.com, который в `noProxy` списке. `curl -sS "$HTTPS_PROXY/__agentproxy/status"` подтверждает через `recentRelayFailures`: `"gateway answered 403 to CONNECT (policy denial or upstream failure)"` — это не сбой конкретного сайта, а сетевая политика окружения (см. `/root/.ccr/README.md`, раздел "403/407 from the proxy"). `WebSearch` при этом работает нормально и отдаёт содержательные результаты.

Это ломает шаг фактчекинга из промпта автора буквально ("открой первоисточник через WebFetch, подтверди вторым источником"), потому что WebFetch недоступен целиком, не только для конкретных заблокированных доменов, как было с api.telegram.org раньше. Обошли так: собрали факты через WebSearch по 8+ независимым публикациям одной новости (включая официальный пресс-релиз компании через BusinessWire) — цифры совпали дословно везде, расхождений не нашли. Это слабее прямого чтения первоисточника, но на практике сопоставимо по надёжности, когда независимых публикаций много и они совпадают.

**Не чинили и не пытались обойти** (см. README: "do not retry or route around it — report the blocked host"). Не знаем, разовый ли это сбой окружения или постоянная политика конкретного `environment_id` — если повторится завтра, это подтвердит постоянство, аналогично истории с блокировкой api.telegram.org.

**Открытый вопрос:** возможно, стоит переформулировать шаг фактчекинга в промпте автора так, чтобы он не требовал буквально WebFetch, а допускал перекрёстную проверку через WebSearch как равноценный метод, раз WebFetch недоступен на уровне окружения. Пока не менялось — решение за пользователем.

**Закрыто 2026-08-05:** формулировка в промпт добавлена. Практика показала, что агент четыре дня подряд справлялся сам, подменяя WebFetch перекрёстным WebSearch, и посты выходили фактически чистыми. Причиной сбоя 05.08 это не было.

## Промпты агентов переехали в репозиторий (2026-08-05)

До сих пор промпты автора и редактора существовали только в настройках routine на claude.ai/code. Файла, который можно открыть и почитать, не было ни одного, при том что это самые важные инструкции в проекте. Правила стиля жили в двух местах сразу (в `STYLE.md` и внутри промптов) и могли молча разъехаться.

Теперь инструкции лежат в `prompts/author.md` и `prompts/editor.md`.

**Синхронизации нет, потому что копия одна.** Промпт в routine сведён к тонкому загрузчику: «репозиторий клонирован, прочитай `prompts/author.md` и работай ровно по нему; если файл расходится с этим сообщением, прав файл». Репозиторий клонируется в сессию каждое утро, поэтому правка в файле начинает действовать со следующего прогона сама. Отдельно обновлять что-то на claude.ai/code больше не нужно.

**Что осталось в routine.** Только блок публикации: `git config`, `git add`, `commit` и `push` с настоящим PAT. В публичный файл он поехать не может, поэтому шаг публикации в `prompts/*.md` ссылается на системный промпт, а не повторяет команды. Заглушки `<PAT>` в файлах больше нет, ссылаться не на что.

**Защита от пустого файла.** Если `prompts/*.md` не найден или пуст, агент обязан ничего не публиковать, сообщить об этом в финальном ответе и завершить работу. Без этого он попробовал бы восстановить инструкцию по памяти и выдал бы пост мимо всех правил.

**Что это меняет на практике.** Правило стиля теперь живёт в одном месте. Раньше `STYLE.md` и промпт были двумя копиями, которые расходились молча, и `CLAUDE.md` предупреждал об этом отдельным пунктом.

**Риск.** Прогон стал зависеть от одного файла в репозитории. Сломанный или случайно удалённый `prompts/author.md` останавливает выпуск целиком. Сторож это поймает в 11:00, потому что `DRAFTS.md` не обновится.

**Про запрещённые обороты.** На шести постах видно, что «именно», «не X, а Y» и «поэтому» перед выводом — не следы быстрой правки, как записали 31.07, а обычная речь Лизы: обороты есть в пяти постах из шести. Прежнее объяснение в `EXAMPLES.md` заменено. Сам запрет для агента остался строгим: в живом авторском тексте эти конструкции звучат нормально, в машинном читаются как след модели, поэтому ограничение на агента жёстче, чем на автора.

Правил там нет ни одного, только ссылки на блоки F и T/F/X/M/Z — правило по-прежнему живёт в `RULES.md`. Блок стоит в начале намеренно: критерий, прочитанный после работы, — это чек-лист, прочитанный до неё — цель.

**Отдельно про «файл, который записан».** Пункт про перепроверку по файлам, а не по памяти, добавлен не для симметрии: ШАГ 4.5 уже ловил случай, когда самопроверка делалась по впечатлению от текста.

**У редактора блок свой, а не копия.** В `prompts/editor.md` шесть пунктов: каждое утверждение проверено по источнику, у каждого поста есть вердикт, `selfcheck.md` сверен, `REVIEW.md` перезаписан одним блоком, push вернул успех, финальный ответ содержит статус и текст. Отдельно оговорено, что чистый разбор без замечаний — полноценный результат: у автора критерий может выдавить слабый пост ради обновления файла, у редактора — выдуманную претензию ради объёма. Это одна и та же поломка, и лечится она одинаково — тем, что критерий требует проверки, а не находки.

**Ноль постов — третий статус у сторожа.** Легального пути «сегодня тем нет» в конвейере не было, и оба поведения давали ложную тревогу: не трогать `DRAFTS.md` — сторож в 11:00 пишет «прогон дошёл не до конца», перезаписать пустым — `send_drafts.py` не находит блоков и роняет Action. Автор канала подтвердила, что чинить надо кодом.

Заведён `pipeline/no-topics.md`: в пустой день автор пишет туда дату, обойдённые категории источников, найденные темы и ID, по которому каждая отсеялась, и пушит вместе с остальным. `watchdog.py` проверяет этот файл **первым** — если он сегодняшний, уходит спокойное «прогон состоялся, тем не нашлось» с причинами из файла, а три обычных файла в этот день не проверяются вовсе: их и не должно быть. Логика прогнана на четырёх сценариях (пустой день, нормальный день, сорванный прогон, автор дошёл — редактор нет), поведение то, что задумано.

**Файл — сигнал, а не отчёт, поэтому в промпте стоит запрет.** Обновив `no-topics.md` в день, когда посты вышли, агент заглушил бы тревогу о собственном сбое. Прямо это и написано в `prompts/author.md`, рядом с запретом выдавливать слабый пост ради обновления файлов. Обе поломки одного рода: критерий выполняется формально, а не по существу.

Редактор в ШАГЕ 1 теперь тоже различает два случая. Раньше он на любой несегодняшний `DRAFTS.md` докладывал «прогон не состоялся», что в пустой день неправда: есть `no-topics.md` — пересказывает причины, нет — сбой.

## Правило про жирный состояло из одного потолка (2026-08-06)

Пост про Record a Skill автор канала опубликовала текстом агента, без правки — первый такой случай. Единственная претензия: в тексте нет ни одного жирного фрагмента.

Проверяя новое правило, стоит спрашивать не только «что оно запрещает», но и «выполняется ли оно пустотой».

## Инцидент 403 разобран: Authorized не равно Installed (2026-08-06)

Прогон 06.08 был оставлен нетронутым как чистый тест — повторится ли вчерашний сбой.
Повторился, и в этот раз сессия дошла до двух разных отказов вместо одного.

- Прямой `git push` с PAT из системного промпта — HTTP 403.
- Запасной путь через GitHub MCP `push_files` — `403 Resource not accessible by integration`.

**Причина второго отказа найдена и устранена.** На странице
`github.com/settings/installations` две вкладки: **Installed GitHub Apps** и
**Authorized GitHub Apps**. Claude был только во второй. Авторизация разрешает
приложению действовать от имени аккаунта и покрывает чтение; право записи в
конкретный репозиторий даёт только установка приложения на этот репозиторий.
Отсюда и дословная формулировка ошибки — «not accessible by integration».
Приложение установлено на `laperouse-ai-channel` 06.08 через
`github.com/apps/claude`.

Тот же диагноз описан в issue `anthropics/claude-code#57009` (закрыт как not
planned): у автора Claude числился авторизованным OAuth-приложением, но «has not
been installed on any accounts», push стабильно отдавал 403, и в тексте ошибки
виден переписанный remote `http://127.0.0.1:/git/owner/repo/` — то есть git в
контейнере ходит через локальный прокси, а не напрямую.

**Довод «чтение тем же токеном работает, значит виноват токен» не работает.**
Репозиторий публичный: `git ls-remote` и клон проходят вообще без учётных
данных, и с просроченным токеном в URL тоже. Успешное чтение не сообщает о
токене ничего. Сессия построила на нём вывод «похоже на протухший или
недостаточный по правам PAT» — вывод не обоснован, хотя сама версия остаётся
непроверенной.

**Что проверено и исключено.** `master` не защищён: запрос
`branches/master/protection` отвечает 404 «Branch not protected», список
`rulesets` пуст. Версия «push отклоняет защита ветки» закрыта.

**Осталось открытым: жив ли PAT.** Проверка 05.08 давала HTTP 200 с правами
`push` и `admin`, то есть в день сбоя токен был рабочий, и версия про истечение
срока с этим не сходится. При этом сессия 06.08 после отказа посмотрела
`curl "$HTTPS_PROXY/__agentproxy/status"` и получила пустой `recentRelayFailures`:
прокси запрос пропустил, 403 пришёл от самой GitHub. Это довод в пользу того, что
дело всё-таки в токене, а не в сети — но он же не отличает протухший токен от
ограничений git-прокси. Решающая проверка — push тем же токеном с ноутбука, где
сети ничто не ограничивает: прошло — значит 403 даёт облачное окружение, упало —
токен перевыпускать сейчас, а не в октябре.

## Сетевая политика окружения настраивается, а не задана намертво (2026-08-06)

Вывод от 29.07 «UI-настройки сетевой политики для Environment не нашли, значит
ограничение непреодолимо» неверен. У cloud environment есть уровень сетевого
доступа с четырьмя значениями: **None**, **Trusted**, **Full**, **Custom**. По
умолчанию стоит **Trusted** — это конкретный allowlist пакетных реестров,
облачных API и части сервисов Anthropic. Запросы мимо списка падают с `403` и
заголовком `x-deny-reason: host_not_allowed`.

**Этим полностью объясняется находка 01.08**, когда «403 на всё, включая
нейтральные хосты». `example.com` и `google.com` в списке отсутствуют.
`anthropic.com` — тоже: в списке есть `api.anthropic.com`, `claude.ai`,
`docs.claude.com` и `code.claude.com`, но не голый домен. `api.telegram.org`
отсутствует. Ни одного исключения из правила там не было — был обычный allowlist.

**Где настраивается.** На `claude.ai/code` в строке над полем ввода есть облачная
иконка с именем среды; при наведении на среду в списке появляется шестерёнка. В
диалоге — поле **Network access**, значение **Custom**, домены по одному в строке
в **Allowed domains**, и галка «Also include default list of common package
managers», чтобы не потерять реестры. Отдельной страницы настроек у среды нет,
только этот селектор — поэтому в июле его и не нашли. Для routine тот же диалог
открывается из формы редактирования.

**Следствия.** `WebFetch` чинится добавлением доменов источников. Блокировка
`api.telegram.org` тоже снимается — то есть запрет на curl в шаге публикации
держался на диагнозе, которого больше нет. Менять не стали: публикация через
GitHub Action уже работает и не зависит от сетевой политики Anthropic, а прямой
curl из агента снова сломается при следующем изменении окружения.

**GitHub ходит мимо этого уровня.** Все операции с GitHub идут через отдельный
выделенный прокси, независимо от уровня доступа среды: настоящие креды остаются
вне контейнера, а git внутри работает по подменному. У этого прокси свои
ограничения — push разрешён только в текущую рабочую ветку сессии, клон, fetch и
операции с PR работают обычным образом. Для routine отдельно оговорено: ветки с
префиксом `claude/` принимаются всегда, а push в любую другую ветку проверяется
заранее и отклоняется, если ветка защищена, если с неё открыт чужой PR или если
на ней есть коммиты не твоего авторства.

**Запасной путь, если запись в `master` снова упрётся.** Оба workflow
(`publish-drafts.yml`, `publish-review.yml`) триггерятся по `push` с фильтром
только по путям, без `branches:`. Значит push в ветку `claude/*` запустит Action
так же, как push в `master`, и править workflow не понадобится — останется только
решить, как сводить ветку в `master`.
