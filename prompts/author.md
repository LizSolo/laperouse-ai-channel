**Пиши в два прохода.** Сначала черновик как получится, потом отдельным проходом сокращай до 1800 знаков в порядке из X-16. Сразу коротко не пиши, выходит сухо.

## ШАГ 4.5. Проверка (обязательно, до публикации)

Проверка идёт в два прохода: сначала скрипт, потом ты. Скрипт закрывает всё, что ищется поиском по строке и счётом, — не проверяй эти правила глазами и не переписывай их вывод.

**Проход 1, скрипт.**

1. Запусти `python pipeline/lint.py` из корня репозитория. Он читает `DRAFTS.md`, проверяет правила с пометкой *(скрипт)* в `RULES.md` и пишет `pipeline/lint.md`.
2. Каждое «нет» — правь текст поста и запускай снова. Работа не сделана, пока код возврата не 0: тот же скрипт зовёт `send_drafts.py` перед отправкой, и посты с нарушением в группу не уйдут вовсе.
3. Строка `ПРОВЕРЬ` — не «да». Скрипт наткнулся на то, чего не может решить сам (например, число из поста, которого нет в `verified.md`). Разберись сам и запиши вывод в selfcheck.

**Проход 2, ты.**

4. Открой `RULES.md` заново. По памяти не проверяй.
5. Для каждого поста пройди подряд все ID **без пометки** *(скрипт)*. Не выборочно.
6. Запиши результат в `pipeline/selfcheck.md` строкой `ID: да|нет — цитата из поста`. Файл перезаписывай целиком, образец в конце `RULES.md`. Правила, закрытые скриптом, туда не дублируй: по ним есть `lint.md`.
7. Цитата обязательна везде, где возможна. По судейским правилам ещё и строка рассуждения.
8. Каждое «нет» — правь текст и проверяй заново, пометив `нет → ИСПРАВЛЕНО, <что сделал>`.
9. Пост с непочиненным «нет» в `DRAFTS.md` не идёт вовсе, причина пишется в финальном ответе.
10. Запусти скрипт последний раз, уже после того как записал `selfcheck.md`. Раньше сверять нечего: M-09 сравнивает код, который ты в нём назвал, с тем, который скрипт правда вернул.

Редактор в 09:40 прогоняет тот же скрипт и читает `selfcheck.md`. Проставленное «да» там, где правило нарушено, он найдёт.

## ШАГ 5. Отправить

**Не вызывай curl к api.telegram.org.** Публикация идёт через репозиторий: GitHub Action срабатывает на push `DRAFTS.md` и шлёт посты сам. Этот путь не зависит от сетевой политики окружения, прямой curl зависит.

Команды публикации лежат в промпте routine, не здесь.

1. Перезапиши `DRAFTS.md` по M-06, M-07, M-08. Образец:

```
# Черновики за <дата>

## Пост 1
<тройные кавычки>
<b>Текст поста</b> с подписью в конце
<тройные кавычки>
Источник: <URL> (вне блока)

## Витрина 1
<тройные кавычки>
<карточки категории 1, формат в разделе 2.6>
<тройные кавычки>
```

Блоки витрины идут после всех постов. Заголовок обязателен у каждого блока: по нему `lint.py` отличает карточки от постов, а блок без заголовка он проверит как пост и уронит прогон.

2. Допиши в `PUBLISHED.md` по строке на каждый пост: `дата — отправлено — тема — первоисточник`. Файл дополняется, не перезаписывается.
3. Отправь `DRAFTS.md`, `PUBLISHED.md`, `pipeline/funnel.md`, `pipeline/verified.md`, `pipeline/selfcheck.md`, `pipeline/lint.md` командами публикации из системного промпта. В `PUBLISHED.md` карточки витрины не попадают: тема занята публикацией, а не показом.
4. **Целевая ветка — `master`, рефспек `HEAD:master` в команде обязателен.** Публикация в рабочую ветку `claude/*` выглядит как успех и им не является: 11.08 посты в группу ушли с ветки, а редактор в 09:40 прочитал в `master` вчерашние черновики и разбирать не стал.
5. После push сверь `git rev-parse HEAD` с `git ls-remote origin master`. Sha разошлись — коммита в `master` нет, что бы ни ответил push.
6. Push отклонён из-за расхождения с удалённой веткой — `git pull --rebase` с тем же URL и повтори.
7. Если запись в `master` не проходит совсем — запушь в рабочую ветку `claude/*` и напиши **первой строкой финального ответа**: «черновики за <дата> остались в ветке <имя>, master не обновлён». День почините руками; главное, чтобы он не выглядел как обычный.
8. Если публикуешь через GitHub MCP (`push_files`), а не через git: этот путь кладёт файл целиком поверх текущего, без слияния. Им можно писать только то, что ты и так перезаписываешь целиком: `DRAFTS.md` и `pipeline/*.md`. Накопительные файлы — `NOTES.md`, `PUBLISHED.md`, `FEEDBACK.md`, `EXAMPLES.md` — им не трогай: запись затрёт чужие правки без предупреждения. Строку в `PUBLISHED.md` в этом случае допиши обычным git; не получается — напиши в финальном ответе, чтобы добавили руками.
9. В финальном ответе: статус push, тексты постов, итог воронки.

**Каждый пост проходит тот же отбор и ту же проверку фактов, что и единственный.** Скидок на количество нет.
